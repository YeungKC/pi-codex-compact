# Use Codex remote native checkpoints

The extension uses the built-in Codex provider's deterministic Remote V2 Responses compaction path and persists the opaque `compaction.encrypted_content` item instead of generating a local text summary. V1 is selected only by the explicit local feature setting; it is never selected by probing. Codex CLI selects it from provider capability metadata, which Pi does not expose.

Codex-to-Codex model changes record a pending transition without network work. At the first provider request after the change, the extension uses the previous model for remote compaction, reuses the current request's non-input parameters, and persists a custom native checkpoint marked for the newly selected model. For eligible model/request failures, the current model is tried as a fallback; authentication, policy, cancellation, malformed, and unknown protocol failures remain fail-closed. If Pi exposes both models' compaction hashes and they match, the transition is skipped; if either hash is unavailable, the extension fails closed and does not guess a transition. Thinking-level changes do not independently block continuation.

A fork can transform inherited Pi messages before its provider request, so the persisted child branch may not reproduce the provider-input prefix. When a native checkpoint or pending model transition exists, the extension treats the awaited `before_provider_request` input as the authoritative history: it compacts that exact input with the transition history model, persists a checkpoint for the selected model, and retains the last user item when the replacement history omits it. An ordinary mismatch without compaction state remains pass-through. This keeps checkpoint replay aligned with the request Pi actually sends without requiring Pi core to expose a separate fork-history boundary.

Automatic remote compaction runs in Pi's awaited `before_provider_request` hook. It estimates the effective pre-request history plus a JSON-size approximation of the stable system/tool prefix, applies best-effort image/tool weights, and uses a 90% context-window limit when no explicit limit is configured. This is closer to Codex's pre-sampling timing than aborting a completed turn. Pi does not expose Codex's exact tokenizer, mid-turn continuation seam, canonical BodyAfterPrefix baseline, or model capability metadata, so those parts remain explicit approximations. V2 history keeps recent eligible messages within 64,000 tokens, caps retained agent messages at 10,000 tokens, and trims old function-call output before the remote request.

Local text compaction remains delegated to Pi for unsupported providers. Token-budget reset uses the closest Pi compaction boundary because Pi extensions expose no fresh-context-window API. The extension does not claim that custom checkpoint entries are identical to Pi's built-in `CompactionEntry`.
